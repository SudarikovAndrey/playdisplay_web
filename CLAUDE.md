Полная карта — в `CONTENT-MAP.md`. Коротко: в репозитории **только текущий сайт**.


## Деплой — одна команда с Мака (с 29.07.2026)

```
./deploy.sh "текст коммита"
```

Всё остальное скрипт делает сам: снимает залипшие замки git, проверяет ветку,
коммитит правки в `site/` по именам файлов, заливает `site/` прямо на timeweb
через `rsync` и дописывает отчёт в `DEPLOY-LOG.md`. Полное описание — `README-ДЕПЛОЙ.md`.

**GitHub из доставки выведен.** Раньше цепочка была `hybrid-v8` → пересборка `gh-pages`
→ пуш → `git pull` на сервере. Три звена, каждое могло застрять, и застревали.
Теперь сайт обновляется напрямую с Мака, а GitHub остался только резервом истории —
скрипт пушит `hybrid-v8` туда в конце, и если пуш не прошёл, на сайт это не влияет.

**Почему деплой не может идти из чата.** У песочницы Claude сеть открыта только на
`github.com`, до timeweb ей не дотянуться ничем — SSH, FTP и HTTP отдают `403` на прокси.
Поэтому заливку запускает Андрей на своём Маке. Агент готовит коммиты и проверяет, что
уедет, но последнюю команду даёт человек.

Адреса: превью https://sudarikovandrey.github.io/playdisplay_web/ · боевой https://playdisplay.com и https://playdisplay.ru (обе привязаны к одной папке). **Канонический домен — `.com`.** С 19 по 21.08.2026 канон стоял на `.ru` как заплатка, 21.08.2026 возвращён на `.com` по решению владельца. Чем это оплачено — в разделе «Домен .com — единая точка отказа».

**Что на сервере переживает деплой** и никогда не удаляется (список исключений в `deploy.sh`):
`old/` — слепок старого вордпресса; `.git/` — остаток прежнего клона; `.well-known/` — SSL;
`api/config.php`, `api/sessions/`, `api/outbox/` — ключи и рабочие данные ассистента.
Всё прочее, чего нет в `site/`, `rsync` с сервера снимает — и спрашивает подтверждение,
прежде чем удалить.

**Переезд в корень домена состоялся 28.07.2026.** До этого новый сайт жил в подпапке `/new/`, а в корне стоял WordPress 2021 года. Что изменилось:
- WordPress вынесен из веба в `~/wordpress_2/wp_old_root` (база не тронута). Папку `/new/` подняли в корень вместе с `.git`, сама `new` удалена.
- Статичный слепок старого сайта лежит в `~/wordpress_2/public_html/old` → https://playdisplay.com/old/ — 646 файлов, 244 МБ, снят `wget -m -p -k -E -nH`. У него свой `.htaccess` с `X-Robots-Tag: noindex, nofollow`. В архиве 21 страница работ, из них 6 (`jihi-studio-lamp`, `holocube_s`, `petrol-bowl`, `summer-17`, `changi2016`, `оживайка`) на новом сайте отсутствуют — возможно, стоит перенести.
- Герой архивной главной — фоновое видео с Vimeo (id 455829149), wget его забрать не мог. В конец `old/index.html` дописан скрипт-вставка iframe; видео всё равно не проигрывается (нужен приватный хеш встройки), фон сделан чёрным.
- `site/.htaccess` теперь в репозитории и держит редиректы со всех старых адресов вордпресса, закрывает `.git` и задаёт mime/кэш. Раньше `.htaccess` жил на сервере незакоммиченным.

Сборку пакетов для ручной загрузки (был скрипт `build_upload.py` и папка `deploy/`) убрал 27.07.2026, а 29.07.2026 из доставки ушёл и `git pull` — остался один `rsync`.

- **Почему коммиты «застревали» — разобрано 29.07.2026.** Причина не в ветках. Монтированная папка в песочнице разрешает создавать файлы, но **не разрешает удалять**. Git на каждую операцию создаёт `.git/index.lock` и потом снимает его — снять не может, лок остаётся навсегда, и любой следующий коммит из любого чата падает с «Another git process seems to be running». Лечится удалением лока; `deploy.sh` теперь снимает залипшие локи сам (моложе двух минут не трогает — там может работать живой процесс). Если агент упирается в «Operation not permitted» на удалении, ему нужно запросить право на удаление для папки.
- `.github/workflows/deploy-pages.yml` — **отключён 29.07.2026** (`on: workflow_dispatch` вручную). Триггерился на пуш в `proto-3d`, требовал `Settings → Pages → Source: GitHub Actions` и к реальной доставке отношения не имел. Оставлен как рабочая заготовка на случай, если превью на Pages понадобится снова.
- `origin/HEAD` смотрит на `main`, где лежит один «Initial commit» — поэтому GitHub по умолчанию открывает пустую ветку.
- Ветки `master`, `gh-pages-new`, `gh-pages-ready`, `proto-3d` — старьё. Локально удалены 29.07.2026, на GitHub остались как резерв. Не воскрешать.
- Ветка `gh-pages` больше не участвует в доставке. Пересобрана 29.07.2026 из `site/` начисто: до этого в неё случайным `git add -A` уехали `_ARCHIVE` (1056 МБ) и `production` (473 МБ), и весь этот архив раздавался с боевого сайта.
- Локальный тест: сервер в песочнице умирает между вызовами bash; тестировать через file-инструменты или на живом сайте после деплоя.

## Аналитика — `site/analytics.js` (разобрано 17.08.2026)

Один файл на весь сайт: Метрика 111509723 и GA4 G-8L3XFCPG2V, номера счётчиков живут
только здесь. Подключается одной строкой (`<script src="/analytics.js" defer>`) — в
`index.html`, в шаблоне страниц работ внутри `build_seo.py` и в скелете страниц кита.
Внутрь `hero-scene.html` и других встраиваемых сцен НЕ подключается: визит посчитался бы
дважды. Счётчики работают только на боевых доменах (проверка по `location.hostname`),
DNT уважается, цели отправляются одной строкой `pdGoal('название')`.

- **`ssr: true` В ИНИЦИАЛИЗАЦИИ МЕТРИКИ — ЛОВУШКА, СТОИВШАЯ ПОЛУГОДА ДАННЫХ.** Название
  обманывает: это не «сайт отдаётся сервером», а «просмотр я отправлю сам». С этим флагом
  тег грузится, `Ya._metrika` существует, ошибок в консоли нет — и НИ ОДНОГО хита не
  уходит. Метрика показывала нули с февраля по август, пока GA4 рядом честно собирал:
  gtag отправляет `page_view` сам. Проверяется в браузере одной строкой — на загрузке
  должен появиться запрос к `mc.yandex.ru/watch/111509723`. Отсюда общее правило:
  **«счётчик стоит» и «счётчик считает» — разные вещи, проверять надо хит, а не наличие
  скрипта.**
- `trackHash` не включаем: переходы по кейсам отправляются вручную (`ym 'hit'` на
  `hashchange`), иначе визит удвоится.
- **Проверка по отдаваемому HTML ничего не доказывает:** скрипт подключён с `defer`, в
  разметке видна одна строка. Смотреть надо в браузере — сетевые запросы и `typeof ym`.

## Домен .com — единая точка отказа (19.08.2026)

`playdisplay.com` истёк 18 августа, и **лёг весь сайт целиком, включая живой `.ru` и закрытые
презентации**: первым правилом в `site/.htaccess` стоит 301 «всё, кроме канонического домена»,
и `.ru` честно перебрасывал посетителя на мёртвый домен.

- **Регистратор — RU-CENTER (nic.ru), не timeweb** (в панели хостинга у обоих доменов «Домен не у нас»).
  Срок оплаты видно в `hosting.timeweb.ru/domains`, колонка «Оплачен до». `.com` — 18 августа,
  `.ru` — 22 декабря.
- **Диагноз читается по симптому.** `ERR_NAME_NOT_RESOLVED` — домен снят с делегирования
  (`clientHold`, реестр убрал его из зоны, записи в панели timeweb при этом целы и спрашивать их
  некому). `ERR_CONNECTION_REFUSED` — домен уже разрешается, но НЕ туда: после оплаты RU-CENTER
  оставил NS на своей парковке `dnsproxy1/2.fm.nic.ru` → адреса `31.177.76.32 / 31.177.80.32`,
  а парковка слушает только `:80`, `:443` закрыт. **Оплата домен возвращает, делегирование — нет,
  NS надо править руками** на `ns1.timeweb.ru`, `ns2.timeweb.ru`, `ns3.timeweb.org`, `ns4.timeweb.org`
  (взяты у рабочего `.ru`).
- **Проверять надо хостинг отдельно от домена**, иначе чинишь не то:
  `curl -sI --resolve playdisplay.com:443:188.225.12.110 https://playdisplay.com/` → `200`, то есть
  сайт цел, а `188.225.12.163` (адрес `.ru`) на SNI `.com` отказывает — у доменов разные адреса и
  разные сертификаты, это норма.
- **Как переключается канонический домен** — пять мест и одна команда: `BASE` в `build_seo.py`,
  `site/.htaccess` (правило канонизации И 17 правил редиректов — в них домен написан целиком,
  см. ниже почему), головы `site/index.html`, `site/privacy.html` и `site/digital/index.html`
  (в `digital` ещё ссылка логотипа в разметке), потом `python3 build_seo.py`. Всё остальное — sitemap, robots, llms, hreflang, JSON-LD, страницы
  работ и услуг — пересчитается само. Проверка: `grep -rn playdisplay.ru site/` должен оставить
  только комментарии в `.htaccess`.
- **19.08.2026 канон срочно перевели на `.ru`** — заплатка на время, пока `.com` лежал: ждать
  возврата NS было нельзя, у делегирования `.com` на уровне реестра TTL двое суток.
  **21.08.2026 канон возвращён на `.com`** по решению владельца: домен восстановлен, NS у timeweb,
  сертификаты на всех четырёх именях (`.com`, `www.com`, `.ru`, `www.ru`) действуют. Возврат сделали
  на второй день НАМЕРЕННО — за двое суток на `.ru` ничего не склеилось, и переигрывать нечего.
  Чем позже такой возврат, тем он дороже.
- **ЦЕНА КАНОНА НА `.com`, и её не лечит конфиг.** Пока `.ru` отдаёт 301 на `.com`, смерть `.com`
  роняет сайт целиком — вместе с живым `.ru` и закрытыми презентациями. Именно это и случилось
  18–19.08.2026. Apache не умеет узнать, что домен снят с делегирования, поэтому защита одна:
  `.com` не должен истекать — автопродление у регистратора и оплата на несколько лет вперёд.
  Если от зависимости решат избавиться, снимать надо ПРАВИЛО КАНОНИЗАЦИИ в `site/.htaccess`
  (оставив `canonical` в разметке), а не менять `BASE`: тогда падение `.com` теряет сайт из
  выдачи, но не из сети.
- **В редиректах `.htaccess` адрес пишется целиком, и это не лень (21.08.2026).**
  Относительная подстановка с флагом `R=301` отдаёт `Location` со схемой, которую видит САМ
  Apache, а TLS здесь терминирует прокси — Apache видит `http`. На боевом `/projects` отдавал
  `301 → http://playdisplay.com/#work`, после чего срабатывал ещё один редирект `http→https`:
  два хопа вместо одного и незащищённый промежуточный адрес. Схему из `.htaccess` не подменить,
  поэтому во всех 17 правилах стоит абсолютный `https://playdisplay.com/…`. Проверяется одной
  строкой: `curl -sI https://playdisplay.com/projects | grep -i location` — в ответе должен быть
  `https`, а не `http`.
- **Закрытые презентации (`/ball/`, `/avtovaz/`) канонизации НЕ подчиняются и отвечают на
  обоих доменах.** Ссылки на них разосланы партнёрам и не должны зависеть от того, какой
  домен сегодня канонический. Само это выходит из тонкости Apache: у папок свои `.htaccess`
  с `RewriteEngine`, а он отменяет правила родителя (без `RewriteOptions InheritDown`
  они не наследуются). Полагаться на тонкость нельзя, поэтому в `site/.htaccess` стоит
  ЯВНОЕ исключение — новую презентацию дописывать туда же. Важно и почему: вместе с
  доменом сменилось бы печенье доступа, и партнёр увидел бы запрос пароля вместо документа.
- Все `@playdisplay.com` в `site/api/` и в `index.php` презентаций — это адреса почты и SMTP-имя,
  их при смене домена НЕ трогать. Ссылки на `playdisplay.com/wp-content/uploads/…` в `projects.json`
  — мёртвый запасной источник обложек ещё с переезда в корень (отдаёт 301 на главную), тоже не трогать.

## Конструктор презентационных страниц — `site/kit/` (с 11.08.2026)

Блоки, из которых собрана книга «Музей Мяча», плюс приёмы лендинга — вынесены в
самостоятельный кит, чтобы новые страницы собирались из готового, а не переписывались.
**Навык `playdisplay-pages`**: в новом чате достаточно сказать, что нужно сверстать
страницу на ките, и агент сам прочитает опись и откроет каталог.

- `blocks.json` — опись 33 блоков: зачем, разметка, файлы, опции и `traps` — то, что уже
  ломалось. Это главная ценность файла: пороги, счётчики кадров, ловушки `object-fit: cover`,
  поведение `scroll-behavior: smooth`.
- `catalog.html` — живой каталог. Проза берётся из `blocks.json`, а РАЗМЕТКА печатается из
  самой демонстрации, поэтому показанный код не может разойтись с показанным видом. Каталог
  сам считает, для каких блоков нет демо, и пишет это в строке состояния.
  Смотреть через `python3 serve.py` → `/kit/catalog.html`; с диска не работает — `fetch` описи
  на `file://` запрещён.
- `new-page.py` — скелет новой страницы с подключённым китом. Ключ `--private "пароль"`
  собирает закрытую страницу тем же способом, что книга: вёрстка в `private/`, проверка в
  `index.php`, в файлах только соль и отпечаток PBKDF2. Генератор, а не «скопируйте книгу»:
  копия тянет за собой чужое содержание и чужие частные правки.
- Правило развития: **новый блок сразу кладётся в кит** (css/js + запись в описи + демо в
  каталоге). Иначе следующий чат изобретёт его заново и сделает иначе.
- Кит — независимая копия: книга `site/ball/` НЕ переведена на него сознательно, это
  выпущенный документ, его не редактируем. Расхождение допустимо, единственный источник
  правды для новых страниц — кит.

## Закрытая концепция «Музей Мяча» — `site/ball/` (с 07.08.2026)

Сверстанная книга концепции для партнёров. Ссылок с сайта нет, в sitemap нет, доступ по
прямому адресу `/ball/` и паролю. Русский язык, вне двуязычия лендинга.

- **Проверка на сервере, а не в браузере.** Книга лежит в `ball/private/page.html`, куда
  веб-сервер не пускает вовсе (`private/.htaccess`), и отдаётся `ball/index.php` только
  после пароля. При клиентской проверке вся вёрстка читалась бы через «просмотр кода».
  В файлах хранится соль и отпечаток PBKDF2-SHA256 (200 000 итераций), пароля нет.
  `index.php` написан НАМЕРЕННО старомодно (без `strict_types`, без массива в `setcookie`,
  со своей реализацией PBKDF2): версию PHP на шаред-хостинге меняют без предупреждения,
  и на новом синтаксисе POST падал пятисоткой при верном пароле. Диагностика — `/ball/?diag`.
- **Локально книгу смотреть по адресу `/ball/`, а не файлом из `private/`.** `serve.py` php
  не исполняет, поэтому он сам отдаёт книгу по `/ball/`, а заход в `private/` перебрасывает
  туда же. Прямой заход давал страницу БЕЗ стилей: пути к `css/` относительные и от
  `private/` уезжают на уровень глубже. На этом потеряли время 07.08.2026.
- **Мяч на первом экране — `ball/js/ball.js`**, облако из 27 000 точек, шесть видов спорта
  по кругу (футбол, баскетбол, теннис, волейбол, бейсбол, гольф) со сменой раз в 4 секунды
  и по клику. Порядок не случайный: у тенниса и бейсбола ОДИН шов, подряд они читаются как
  один мяч. Что выяснилось замером, а не рассуждением: (1) точки СБИТЫ со спирали Фибоначчи
  случайным сдвигом — на таком количестве её витки становятся главным узором и глушат
  рисунок мяча; (2) рисуем `fillRect`, а не `arc` — круги в кадр не укладывались;
  прозрачность округляется до шести ступеней и запечена в строки `rgba`, чтобы в кадре
  менялся только `fillStyle`; (3) роль точки (поле/полутон/шов) считается один раз в таблицу
  `Uint8Array` на каждый мяч. Роли РАЗНЫЕ по смыслу у разных мячей: фон почти чёрный,
  поэтому тёмная точка рисует не линию, а пропуск — у гольфа, волейбола и баскетбола шов
  самый тусклый, у футбола наоборот.
- **Рисунки мячей заданы геометрией, а не «на глаз».** Футбол — диаграмма Вороного 32 точек
  (вершины икосаэдра дают 12 пятиугольников, вершины додекаэдра — 20 шестиугольников), шов
  считается РАССТОЯНИЕМ ДО ПЛОСКОСТИ-БИССЕКТРИСЫ `(p·a − p·b)/|a − b|`, а не разницей
  скалярных произведений: разница растёт от границы с разной скоростью и у углов, где
  сходятся три панели, мала на большой площади — шов пухнул там в пятна и съедал углы
  панелей. Палитра как на фотографии: белые шестиугольники, тёмно-серые пятиугольники,
  почти невидимый шов. Пятиугольник в ноль делать нельзя — он превращается в дыру, и
  белые шестиугольники вокруг сливаются в неопознаваемый лоскут. Теннис и бейсбол — «теннисная кривая»
  `x=(1−λ)cos t+λcos3t, y=(1−λ)sin t−λsin3t, z=2√(λ(1−λ))sin2t`, лежит на сфере точно.
  Швы считаются расстоянием до ВЫБОРКИ точек кривой: раньше баскетбол мерил «расстояние до
  плоскости с волной», и там, где её уровень идёт по поверхности касательно, полоса
  раздувалась в клин — это и была видимая ошибка. Пороги проверяются замером доли площади:
  у футбола порог, взятый на глаз, отдавал шву 70 % шара.
  **Баскетбол — РОВНО ТРИ шва:** экватор, прямой меридиан и третий с волной по долготе.
  Четвёртая линия лишняя: спереди волнистое кольцо видно как две «скобки» по бокам — это
  его передняя и задняя половины, а не два разных шва. Три взаимно перпендикулярных кольца
  дают восемь панелей, как у настоящего мяча.
- **Курсор-мяч не подменяется мгновенно.** У него четыре состояния: точка, слёт частиц в
  мяч, мяч, разлёт с возвратом точки; прежний курсор гаснет на слёте и включается в конце
  разлёта, поэтому двух курсоров в кадре не бывает. Счётчики проверок зоны и касания
  строки РАЗНЫЕ: на одном общем внутри зоны он растёт вдвое быстрее, одна из проверок
  получала только нечётные значения и не срабатывала никогда — так пропадали и выход из
  зоны, и разлёт по строкам. Повторный разлёт разрешён только после ухода с текста: во
  вступлении две строки, курсор задевал то одну, то другую, каждая считалась новой, и мяч
  почти всё время был в разлёте.
- **Рентген купола на кадре арены — `ball/js/xray.js`.** Под курсором проявляется круг в
  200 точек, в нём видна сетка несущей конструкции. Слой — не присланный обрезок, а
  картинка В ПОЛНЫЙ РАЗМЕР базовой: базовая выведена через `object-fit: cover`, её верхняя
  грань при других пропорциях окна уезжает за кадр, и «состыковать по верхней грани»
  средствами CSS было бы нечем. Слой того же размера с тем же `cover` совпадает с базой
  пиксель в пиксель при любом окне. В слое оставлены ТОЛЬКО ЛИНИИ: положительная разница
  присланного рендера с базовым (`max(0, xray − base)`) с мягким порогом — иначе в круге
  прыгала экспозиция, у двух рендеров она разная. Низ сведён в прозрачность, поэтому ниже
  верхней части проявлять нечего, и граница не читается прямой линией. Пятно — маска
  радиальным градиентом: у `clip-path` край всегда резкий.
- **Курсор-мяч включён ТОЛЬКО на двух экранах** — «Мяч — проводник» (`.opening-statement`)
  и финальном с контактами (`#contacts`). На остальных страницах возвращается прежний
  курсор-точка со свечением: на плотном тексте и фотографиях мяч в 15 % высоты экрана
  закрывает содержание и рвётся на каждой второй строке.
- **Курсор на книге — тот же мяч из точек, 15 % высоты экрана** (`.ball-cursor`). Касание
  строки текста разрывает его на точки, и собирается уже следующий мяч. Два подвоха:
  (1) у курсора СВОЁ облако — сначала он брал каждую девятую точку большого, и на трёх
  тысячах точек снова проступала спираль Фибоначчи; (2) рисунок огрубляется множителем
  `WIDE` (у гольфа заодно режется число лунок), иначе шов в долях радиуса уходит в один
  пиксель и баскетбольный мяч выглядит ровно оранжевым. Касание считается по строкам
  (`Range.getClientRects`), а не по рамке абзаца, и строка «разряжается» — иначе курсор,
  оставленный на тексте, взрывался бы каждую секунду.
- **Проверять рисунок мячей можно без браузера:** тот же код прогоняется в node и рисуется
  в PNG орфографической проекцией. Так нашлись и спираль в курсоре, и клинья баскетбола,
  и красная полоса вместо стежков у бейсбола.
- **Разметка площадок на фоне — `ball/js/courts.js`.** В текстовых главах под содержанием
  едва заметная разметка из точек: вид сверху, по мере прокрутки складывается в
  перспективу и гаснет у горизонта, через главу появляется следующая. Достаётся ТОЛЬКО
  главам без иллюстраций, и они находятся сами (`.chapter` без `figure`) — список руками
  пришлось бы помнить при каждой правке содержания. Размеры площадок настоящие, в метрах
  (теннис 23.77×10.97, поле 105×68, баскетбол 28×15, сквош 9.75×6.4): «похоже на глаз»
  не опознаётся. Перспектива считается камерой, наклонённой над плоскостью
  (`d = H·cos a + v·sin a`, `sy = (v·cos a − H·sin a)/d`), а не CSS-трансформацией:
  трансформация повернула бы прямоугольник, а у нас точки, и проецировать надо каждую.
- **Мягкая прокрутка и кнопка «в начало» — `ball/js/ui.js`.** Здесь важна одна ловушка:
  у страницы задан `scroll-behavior: smooth`, и браузер превращает В ПЛАВНУЮ КАЖДУЮ
  программную прокрутку. Кадровый лерп на этом ломался — анимации гасили друг друга, и
  за 700 мс страница проезжала 17 пикселей вместо трёхсот. Внутри цикла прокрутка только
  мгновенная (`behavior: 'instant'`), плавность даём сами. Тачпад не перехватываем: там
  инерция своя, и вмешательство делает её двойной.
- **Заставка книги — `ball/js/boot.js`.** Слой лежит В РАЗМЕТКЕ, а не создаётся скриптом:
  иначе между показом страницы и запуском скрипта мигает недогруженная вёрстка. Ждём
  шрифты и картинки ПЕРВЫХ ДВУХ ЭКРАНОВ, а не `window.load`: в книге двенадцать тяжёлых
  кадров и два ролика, и полное ожидание держало бы заставку десятки секунд. Полоса
  показывает настоящую долю загруженного. Предохранитель на 8 секунд обязателен —
  документ, отправленный партнёру, не должен остаться чёрным экраном из-за одной
  недошедшей картинки.
- **Подсказки на кадрах — `ball/js/hotspots.js`.** Координаты меток заданы в процентах ОТ
  КАРТИНКИ и пересчитываются в пиксели скриптом, потому что кадры выведены через
  `object-fit: cover`: изображение обрезается по месту, и проценты от рамки не совпадают
  с процентами от картинки — при других пропорциях окна метка уезжает с предмета.
  Пересчёт повторяет геометрию браузера (`scale = max` по ширине и высоте, сдвиг —
  половина обрезки) и запускается заново на resize. Метка — `button`, чтобы подсказка
  открывалась и с клавиатуры, и касанием. У ядра метки тёмный контур: одного свечения
  мало — на белом мяче светлая точка пропадает, на тёмной воде теряется круг.
- **Списки книги оживляет `ball/js/lists.js`** — разбирает содержание и сам выбирает подачу
  (шаги с номерами, карточки, опоры разделов). Текст пунктов не меняется ни на символ.

никогда `git add -A` — добавлять файлы по именам, массово файлы не удалять.

Владелец иногда ведёт несколько чатов одновременно (например миниигра в одном, контент в другом). Изоляции между ними нет: все правят одни и те же файлы на диске, и последняя запись перетирает чужую.

- **Территории.** Миниигра и 3D-сцена — `site/hero-scene.html`. Контент, лендинг, данные, документация — `site/index.html`, `site/data/*`, `*.md`. AI-ассистент — `site/api/*` целиком плюс два блока в `index.html`: панель `#ai` с её CSS и скрипты `window.pdIdea`/`window.pdSpeech`. Связка лендинга с игрой (`pdGame`, `pdPlay`, лоадер) живёт в `index.html` — если её нужно править из игрового чата, сначала сказать владельцу. `index.html` — самый спорный файл: перед правкой перечитать.
- **Перед работой** — `git status` и `git log -1`. Если в рабочей копии чужие незакоммиченные правки, не трогать их и спросить владельца.
- **Коммитит и деплоит один чат.** Два агента в одном `.git` дают залипшие `.git/*.lock` и битый индекс.
- **Деплой запускает владелец, одной командой** `./deploy.sh "что сделали"`. Агент из чата этого сделать не может: у песочницы сеть открыта только на `github.com`, до timeweb не дотянуться ничем. Дело агента — довести правки до коммита в `hybrid-v8` и сказать, что можно деплоить.
- **На сервер уезжает диск, а не коммит.** `rsync` заливает `site/` как она лежит, вместе с незакоммиченным и с файлами, которых в git нет вовсе. В общей папке это значит, что чужая недоделка уедет на боевой сайт. Перед деплоем скрипт показывает незакоммиченное — читать этот список, а не проматывать.
- **Признак столкновения:** Edit не находит фрагмент, который точно был, или файл выглядит иначе, чем ожидалось. Это значит, что файл изменил другой чат — перечитать, а не перезаписывать.

- `site/enemy-lab.html` — конструктор врага (29.07). Форма приходит СВОЕЙ моделью (.obj/.glb/.gltf/.stl/.fbx, drag&drop), вокселизируется по площади треугольников. **Рёбра берутся у меша, а не угадываются по облаку**: `THREE.EdgesGeometry` даёт отрезки по двугранному углу, по ним рассыпается плотная цепочка контурных точек и рисуются сами линии — без этого форма оставалась облаком точек. Поиск по изгибу нормалей остался запасным путём для несваренных мешей. Заливка затенена ламбертом по нормали (свет в координатах камеры) — иначе плоскости не отличались друг от друга. Всё, что мерится в юнитах, считается ОТНОСИТЕЛЬНО габарита: пресет, снятый на дроне в 6 юнитов, работает и на захватчике в 300. Палитра — пипетками, с двумя пресетами: «Как в игре» (ровно цвета gBuildMother) и «Читаемая» — игровая заливка `#1c2130` на аддитивном блендинге исчезает, и от корабля остаются одни линии. Зоны удара расставляются по облаку автоматически при смене модели (низ у центра — реактор, крайние точки бортов — двигатели, верх — мостик) и дальше правятся руками. Урон — растущие пробоины с обугленным полем и горячей кромкой. **Заслон по глубине** (`OCCL`): отсечение отвёрнутых убирает изнанку только ОДНОЙ оболочки, дальний пилон, повёрнутый к нам лицом, всё равно просвечивает через корпус — и тем более линии рёбер, у которых нет ни нормалей, ни глубины. Лечится невидимым проходом той же геометрии, который пишет ТОЛЬКО глубину (`colorWrite: false`, `renderOrder −1`, порог альфы 0.5, глубина сдвинута на `CELL×1.6` дальше настоящей — иначе точка не проходит собственный тест глубины и модель исчезает). Два материала делят один вершинный шейдер и ОДНИ объекты юниформов, различает их `uPass`. На взрыве заслон снимается: обломки летят вперемешку, и взаимное заслонение даёт мигающую кашу. Есть и в лаборатории, и в игре. **Просвет насквозь** (`xray`): отвёрнутые точки не пропадают совсем, а гаснут до заданной яркости — 0 глухая оболочка, 1 модель видно насквозь; число уезжает в игру в `CULL.xray`. **Ядро двигается ползунками** в долях полугабарита; по умолчанию само садится на зону с наибольшим множителем, любая правка ползунка снимает автопривязку. **Взрыв посчитан в закрытой форме прямо в вершинном шейдере** (`p(t) = p0 + (v0 - g/k)(1-e^(-kt))/k + (g/k)t` плюс поворот куска на `|ω|·t`), поэтому таймлайн таскается в обе стороны и картинка детерминирована — в отличие от игрового `gShipCrash`/`gUpdateDebris`, где обломки интегрируются по кадрам и отмотать назад нельзя. Кнопка «Точки для игры» выгружает `enemy-points.js` — **формат v2** (поле `V: 2`): координаты, **нормали** (`NOR`), **зона точки** (`ZN`), размеры точек в мировых юнитах (`PSIZE`), свет (`LIGHT`), отсечение (`CULL`), `EDGEBOOST`/`FILLDIM`, зоны удара в абсолютных юнитах (`ZONESU`), палитра и `BOOM`.

- **Страж от ботов перед разговором (`api/lib/guard.php`, `window.pdGuard`).** Браузер обязан
  решить подписанную HMAC задачу: `sha256(nonce:число)` с 16 нулевыми битами (~65k хешей,
  0,1 с на компьютере). Работа идёт, пока человек читает первый экран, поэтому проверка
  невидима; если не успела — вокруг микрофона заполняется кольцо из точек НАСТОЯЩИМ прогрессом
  перебора. Задача одноразовая, привязана к адресу, живёт 10 минут, сложность растёт до 19 бит
  при частых сессиях. Потолок подобран замером: своя реализация sha256 даёт ~800k хешей/с,
  телефон вчетверо меньше — за 22 бита телефон считал бы 20 секунд, поэтому выше 19 нельзя.
  **По эвристикам поведения отказа не бывает** — только вторая ступень («поймать фазу»,
  доступна с клавиатуры): человек со скринридером выглядит как бот. Своя реализация sha256
  вместо `crypto.subtle` — тот требует защищённого контекста и промисов; наша считается
  синхронно, нарезана по кадрам и проверена побайтово против эталона.

  смыслы (`pd_prompt_words`), перевод карточки (`pd_prompt_card`, только для не-русских
  разговоров, ~300 токенов). Бриф пишется целиком по-русски, `title_ru` снимается ДО перевода.
  Если перевод не удался, показывается русская карточка и пишется строка в лог: половина
  карточки на чужом языке хуже, чем вся на русском — человек решит, что интерфейс сломался.
  **Прежде чем усиливать промпт, проверьте, не просите ли вы двух дел в одном ответе.**
- **ПРОМПТ ПЕРЕВОДА ПИШЕТСЯ НА ЯЗЫКЕ ПЕРЕВОДА, и результат надо ПРОВЕРЯТЬ (04.08.2026).**
  Русская инструкция с русским входом читалась моделью как «оставь как есть»: приходил
  валидный JSON с непереведённым текстом — ошибки нет, в логе тишина, а англоязычный гость
  видит русскую карточку. Теперь `pd_prompt_card()` для en и pt написан по-английски и
  по-португальски, а после перевода заголовок прогоняется через `pd_detect_lang()`: всё ещё
  русский — один повтор, потом честно показываем русскую карточку и пишем в лог. **«Модель
  ответила» и «модель сделала» — разные вещи; проверяйте результат, а не факт ответа.**
- **ЯЗЫК СТРАНИЦЫ — ПЛОХАЯ ДОГАДКА ПРО РЕЧЬ, и это стоило сломанного микрофона (04.08.2026).**
  Гость с русской системой открыл `/en/`, заговорил по-русски — распознавание на `en-US`
  не слышит ни слова и молчит. Определение языка по тексту (`pd_detect_lang`) тут не спасает:
  текста не появляется НИКОГДА, замкнутый круг. Теперь начальная локаль берётся из
  `navigator.languages` (первый поддерживаемый; полная локаль вида `pt-BR` уважается), а
  подсказка сервера в `ping` применяется, только если браузер ничего своего не предложил
  (`pdSpeech.guessed()`). Плюс три кнопки RU/EN/PT под строкой «услышано» — неверная локаль
  не даёт ошибки, микрофон просто молчит, и человеку нужно место, где это поправить самому.
  Плюс сторож тишины: девять секунд без единого слова — подсказка и открытый ввод текстом.
- **SAFARI — отдельный браузер, а не «почти Chrome» (04.08.2026).** На iPhone и на Маке микрофон
  включался — в адресной строке горела запись, — но распознавание не присылало НИ ОДНОГО
  слова. Две причины, обе про Safari: (1) он не тянет `continuous` — с ним результатов нет
  вовсе, поэтому там ведём по одной фразе, а непрерывность делаем сами через `onend`
  (цикл уже был для Chrome); (2) `rec.start()` должен вызываться СТРОГО из жеста
  пользователя, а мы поднимали распознавание в колбэке XHR после `start` — Chrome такое
  прощает, Safari молча отказывает. Теперь микрофон включается в `enter()`, синхронно
  внутри обработчика клика, а `startCapture()` только подхватывает. Плюс в Safari поле
  ввода открывается сразу: там распознавание может не заработать вовсе, и второй путь
  человек должен видеть с самого начала, а не после девяти секунд тишины.
- **Почта: `file` на живом хосте — это потеря запроса, поэтому есть запасной путь (04.08.2026).**
  Драйвер `file` честно сохраняет письмо в `api/outbox` и честно отвечает «успех» — а на почте
  ничего нет. Так потерялся живой запрос: разговор прошёл, интерфейс сказал спасибо, письма не
  было. Теперь `pd_mail_driver()` решает, чем отправлять НА САМОМ ДЕЛЕ: на боевом хосте (не
  localhost и не `*.local`) вместо `file` берётся `mail()` хостинга — письмо в спаме лучше,
  чем письмо в никуда. Локально остаётся `file`, там он и нужен. Копия в `outbox` кладётся
  всегда, когда smtp не настроен: `mail()` не даёт вменяемой диагностики, и файл на диске —
  единственный способ достать письмо. Состояние видно в `ping` (плашка) и в ответе `send`
  (`stored`). **Полноценно это лечится только smtp** — ящик на домене плюс SPF и DKIM.
- **PDF печатается ОТДЕЛЬНЫМ ДОКУМЕНТОМ в новом окне (04.08.2026).** Первая версия прятала
  весь сайт через `visibility: hidden` и оставляла один слой — получался **пустой PDF**:
  панель `fixed`, у `body` во время сессии `overflow: hidden`, и браузеру нечего было
  раскладывать по страницам. Теперь `printBrief()` открывает окно, пишет туда самостоятельный
  html со своими бумажными стилями и печатает его; логотип — по абсолютному адресу через
  `document.baseURI`, иначе в новом окне относительный путь считать не от чего. Заголовок
  документа = название проекта: Chrome подставляет его как имя файла. Слой `#aiPrint` остался
  запасным путём, если блокировщик не даёт открыть окно.
- **«Скачать PDF» — это печать браузером, а не свой генератор.** Слой `#aiPrint` виден только
  в `@media print`: белый фон, чёрный логотип (`playdisplay-logo-black.png`), бумажная вёрстка.
  Своего PDF нет сознательно: jsPDF пришлось бы тащить с CDN вместе со шрифтом с кириллицей
  (штатные шрифты jsPDF её не умеют) — две зависимости ради одной кнопки, и обе ломают
  самодостаточность `site/`. `visibility`, а не `display`: панель ассистента `fixed`, и
  `display:none` на родителе ломает поток.
- **На экране результата — ВСЁ собранное блоками.** Раньше показывалась только карточка, а
  подробности «оставались на сервере»; это его собственные слова, скрывать их незачем. Блоки
  приходят из `brief` готовыми (`blocks`, `questions`, `quotes`, `labels`) — подписи на языке
  гостя из `pd_block_labels()`, пустые не присылаются. Для не-русских разговоров тот же
  проход перевода теперь переводит и блоки, и открытые вопросы (`brief_screen`, `open_screen`);
  в письме студии они остаются русскими.
- **Доска ПЕРЕРАСКЛАДЫВАЕТСЯ при смене вопроса, и это обязательно.** Свободная полоса зависит
  от высоты вопроса, а он меняется на каждом ходу: «Где это будет?» — одна строка,
  «Планируете разместить музей в новом здании или переоборудовать существующее?» — четыре.
  Слова, поставленные при коротком вопросе, оказывались ПОД длинным (видно на скриншоте с
  боевого 04.08.2026). `relayoutWords()` сохраняет углы и радиусы — доска не перемешивается,
  а подбирается под новые границы переходом; столкновения после сжатия полосы разводятся
  сдвигом вдоль своего кольца. И пачка смыслов за ход сдвигает доску ОДИН раз (`addWords`):
  три слова в ответе давали тройной сдвиг, и это читалось как рывок.
- **Когда модель говорит «хватит», экран обязан измениться.** Служебную фразу без
  вопросительного знака мы не ставим заголовком (человек читает её как обращение к себе),
  но раньше просто выходили из `ask()` — экран не менялся вовсе, и это выглядело зависанием
  ровно на вопросе про бюджет, который модель задаёт последним. Теперь подзаголовок говорит
  «материала достаточно», а кнопка сбора получает класс `call` и дышит рамкой.
- **Доска смыслов: свежее у центра, прежнее уходит к краям (04.08.2026).** Слова копятся,
  а не мелькают: каждое новое отодвигает все прежние наружу на 0.09 полуполя, они мельчают
  и гаснут, а за краем (`r > 1.0` — это ровно рамка) снимаются. На большой доске держится
  9–11 слов одновременно, на телефоне 2–3. Место для нового ищется ТОЛЬКО во внутренней
  половине (`look(0.42)`); занято — раздвигаем прежние ещё раз, и лишь в крайнем случае
  пускаем слово дальше. Без этого на узком экране новое слово вставало ДАЛЬШЕ старого и
  доска читалась наоборот. Габарит считается по `placed[].box`, а не пересчётом по базовому
  масштабу: дрейфующее слово уменьшено, и пересчёт давал коробки шире настоящих — на этом
  спотыкался первый вариант теста, а не код.
- **Смыслы раскладываются, а не сыпятся.** Раньше слово вставало в случайную клетку сетки 3×4
  и ни во что не смотрело: слова наезжали друг на друга, лезли под вопрос и под панель ввода.
  Теперь место выбирается: измеряется настоящий габарит слова (`offsetWidth × scale` — масштаб
  меняет вид, но не размер блока), запретные зоны берутся живыми прямоугольниками вопроса и
  `.ai-bottom`, обход идёт кольцами от центра наружу с углами «сначала по бокам». Если места нет,
  **уходит самое старое слово** — облако из четырёх свежих читается лучше, чем из восьми
  наложенных; на телефоне иначе получалась каша. Вопрос закрывается полосой во всю ширину,
  а не своим прямоугольником: он меняет высоту на каждом ходу, и слово, поставленное сбоку от
  короткого, оказывалось под длинным.
- **Копия брифа гостю (04.08.2026).** Отдельная галочка в форме — и человек получает своё
  описание письмом с логотипом студии, на языке разговора (`pd_brief_guest_html`, подписи в
  `pd_guest_labels`). Это НЕ то же письмо: внутренняя часть — подробности, открытые вопросы,
  температура запроса — остаётся у студии; гостю уходит карточка и его собственные слова.
  `Reply-To` ведёт на студию, вложения не пересылаются (он их сам и прислал). Копия уходит
  только при живом адресе: в общем поле мог оказаться телефон или телеграм.
- **Канал связи со своим контактом.** Ник в телеграме и номер в вотсапе редко совпадают с тем,
  что человек написал в общем поле, поэтому выбор канала открывает поле под него. В письме
  такой канал получает свою строку и кликабелен: `t.me/<ник>`, `wa.me/<только цифры>`.
  Формат `channels` принимает и строку, и `{ch, v}` — кэшированная страница не должна ломать
  отправку.
- **Выход — вылет НАЗАД, а не схлопывание в угол.** Влёт идёт от кнопки виджета, и симметричный
  выход возвращал туда же: панель росла к камере (+Z), потом всё сжималось в угол. Человек уходит
  не в кнопку, а на страницу, поэтому теперь панель отступает в глубину (−Z, `opacity`), сборка
  идёт от центра экрана, а страница приходит классом `ai-rise` (масштаб 1.22 от центра → 1).
- **Ожидание = волны и шарики, а не крутящаяся дуга.** Дуга по контуру микрофона читалась как
  «страница грузится», то есть как поломка. Пока думает модель, от микрофона расходятся три
  круговые волны, а сам микрофон подменяется вращающимися шариками (`.ai-rec.think`). Анимации
  висят ТОЛЬКО на этом состоянии: иначе браузер крутит их всё время, пока панель открыта.
- **`.ai-shell` держит `grid-template-columns: minmax(0, 1fr)`** — не косметика. Без него колонка
  сетки растёт по max-content содержимого, а `#aiCapture` объявлен `width:100%`: замкнутый круг,
  и длинный английский вопрос раздвигал колонку шире экрана, уезжая за оба края.
- **Файл с запросом и правила обработки данных (02.08.2026).** В форме отправки — «приложить
  файл» (pdf/word/powerpoint/excel/картинка, до 10 МБ, до 3 штук) **или** ссылка на облако.
  Загрузка идёт `multipart/form-data` действием `file` и **только в момент отправки, после
  согласия** — недоотправленных чужих файлов на диске не появляется. Расширению не верим:
  `finfo` смотрит, что внутри (офисные форматы 2007+ — это zip, старый libmagic так их и
  называет). Имя на диске своё, случайное; `api/uploads/` закрыт `.htaccess` и исключён из
  деплоя. Файл едет вложением (письмо становится `multipart/mixed`, логотип остаётся внутри
  `related`, чтобы скрепка была одна — настоящая) и **удаляется сразу после отправки**.
  Сроки хранения не декларация: `pd_sweep()` при начале разговора чистит сессии старше
  `keep_days` (180) и брошенные загрузки старше суток — cron на шаред-хостинге может быть не
  настроен вовсе. `site/privacy.html` — черновик правил на двух языках, написанный по факту
  кода; в начале файла список того, что должен дописать юрист. **Числа из конфига напечатаны
  на этой странице словами — менять надо в двух местах.**
- **Модели с рассуждением (gpt-5.x) требуют осторожности:** они тратят выходные токены на
  размышление ДО ответа, и при тесном лимите возвращают пустой `content` с
  `finish_reason=length`. Поэтому в конфиге `reasoning => none`, бюджет реплики 900 токенов,
  брифа — 2600, а `pd_openai_parse()` распознаёт этот случай и пишет прямым текстом, что делать.

## Что отстроено и НЕ ломать при пересборке
- **FlyGL** (site/index.html): WebGL-переход в кейс и обратно. Влёт: прямоугольная волна растворения от карточки с искрами по фронту, пиксельные частицы с motion-стрейком, морфинг обложки в кадр, сборка страницы (кадр+тексты) из объёмного облака, перекраска зерна живым видео. Вылет: растворение страницы без видимого фронта, финальная волна сходится и «упирается» в карточку-цель, интерьер открыт заранее, фиксация-свечение контура + искры на периметре. Отладка: `?flyslow` (×3 медленнее), `window.__flyK=0.5` (заморозка фазы). Фолбэк без WebGL — быстрый фейд. Слабое железо/мобила — реже сетка частиц.
- Ховер карточек: пыль-магнит с соседних обложек (canvas #cards-fx). На мобиле карточки сразу цветные (без ховера).
- Hero: постоянная связка postMessage лендинг↔iframe (pdVisible, pdMeta, pdPlay, pdScroll, pdRotate, pdTapPlay, pdReady, pdGame, pdCam). Тёмный лоадер с белым лого; верхняя панель выезжает по pdReady. Кликабельный логотип → верх страницы. Портрет: FOV авто-подстраивается (portraitFitFov), cover не зумится; тап = play/стоп.
- Кейс-вьюер: медиа (локальное видео/встройки/картинки), плашки-меты, статы, flow-блоки с каскадным появлением (.settled), галереи-листалки, «следующий проект», lightbox.
- Мобильные фиксы: без бокового скролла, user-select off в hero, cursor:none только при pointer:fine (иначе пропадает курсор).

## Посадочные страницы услуг (21.08.2026)

`/services/<slug>/` и `/en/services/<slug>/` — пять страниц под запросы об услугах плюс
хаб `/services/`. Содержание в `site/data/services.json` и `site/data/en/services.json`,
генерация — тем же `build_seo.py`.

**Зачем появились.** Замер Вебмастера: 3 клика за 30 дней, видимость по популярным
запросам 7 %, ВСЕ запросы брендовые. Небрендовый был ровно один — «интерактивный макет
территории с отображением информации через проектор». Ключевые слова жили только в
`<meta keywords>` главной, а этот тег поисковики игнорируют с 2009 года. Кейс на запрос
об услуге не отвечает: он про конкретного заказчика, а человек ищет работу.

- **Slug-и в русском и английском файле обязаны совпадать** — они связывают языки в
  hreflang. Сборка проверяет это утверждением вместе со структурой блоков и списком
  кейсов: разойдутся — упадёт, а не соберёт молча не то.
- **Язык без файла данных просто не генерируется**, и hreflang его не обещает. Отсюда же
  `L.srv_foot`: ссылка на `/services/` появляется в подвале страниц работ только у языка,
  где услуги есть. Иначе `/en/work/*` вели бы на несуществующий раздел.
- Типы блоков в `flow` — те же, что у кейсов (`h`, `p`, `steps`, `notes`, `stats`).
  Неизвестный тип валит сборку.
- Разметка на каждой странице: `Service` + `BreadcrumbList` + `FAQPage`. Вопросы живут
  на странице услуги, а не отдельной свалкой: вопрос цитируется вместе со страницей,
  которая на него отвечает. **Расширенных сниппетов в Google `FAQPage` больше не даёт** —
  их сузили до госсайтов в 2023-м и убрали совсем 7 мая 2026. Тип не отменён, удалять
  не нужно; польза осталась в Яндексе и в цитировании поисковыми ИИ. Держим вопросы
  за содержание, не за сниппет.
- `og:image` — обложка первого связанного кейса. Логотип не годится: `logo.svg` соцсети
  в `og:image` не отрисуют вовсе, а `summary_large_image` требует растр.
- Строки интерфейса («Услуги», «Проекты, где это сделано» и прочие) — в общем словаре
  `site/data/i18n/en.js`, а не рядом с генератором: второй источник переводов рано или
  поздно разошёлся бы с первым.
- На `/services/` пока ведут только подвалы русских кейсов и sitemap. Видимого пункта
  в меню главной нет — правка в разметке SPA, решение по дизайну не принято.
- Ход работы по продвижению целиком — в `ПРОДВИЖЕНИЕ.md`.

## Конвенции
- Правки маленькими коммитами с говорящими русскими сообщениями.
- Стиль кода лендинга: ES5 (var/function), кириллические комментарии, объясняющие «почему».

- SEO: канонический домен задаётся ОДНОЙ строкой — `BASE` в `build_seo.py`; сейчас `.com`. При изменении структуры перегенерить: `python3 build_seo.py` (/work, /services, /en, sitemap, robots, llms, JSON-LD, noscript-блок).
