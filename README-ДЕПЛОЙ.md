# Деплой сайта — одна команда

```bash
cd ~/Work/Web_Playdisplay
./deploy.sh "что сделали"
```

Сайт обновлён к моменту, когда скрипт закончил. Ждать нечего.

## Разовая настройка (один раз, пять минут)

```bash
cd ~/Work/Web_Playdisplay
chmod +x deploy.sh                     # разрешить запуск
cp deploy.conf.sample deploy.conf      # локальные настройки, в git не уезжают
```

Чтобы пароль от сервера не спрашивался каждый раз — положить на сервер ключ:

```bash
ssh-keygen -t ed25519            # если ключа ещё нет, Enter на все вопросы
ssh-copy-id pdisplay@vh432.timeweb.ru
```

**Сделано 23.08.2026** — ключ Мака (`SHA256:SyHW+Y1UspjbR1SlDjrteiNbkvHnzf21f/7ItTmXvdU`)
лежит в `~/.ssh/authorized_keys` на сервере, пароль не спрашивается. Ставили через
веб-консоль в панели timeweb: раздела SSH-ключей у shared-хостинга нет. Побочное
следствие — **деплой стал доступен агенту из чата**, и это меняет правила совместной
работы, см. `ПРАВИЛА-РАБОТЫ.md`. Удалить ключ = вернуть парольный ввод, а неинтерактивный
`rsync` на нём просто упадёт.

**Первый запуск сделать холостым.** Он ничего не меняет, только показывает, что уедет
на сервер и что с сервера снимется:

```bash
./deploy.sh --dry-run
```

В первый раз в списке на удаление будут `_ARCHIVE` и `production` — тот самый архив
на 1.5 ГБ, который случайно уехал на боевой хостинг. Это и надо удалить. Убедись, что
в списке **нет** `old/` — это слепок старого вордпресса, он должен остаться.

## Как запускать

| Команда | Что делает |
|---|---|
| `./deploy.sh "правка галереи"` | коммит + заливка + запись в журнал |
| `./deploy.sh` | заливка без коммита (спросит текст, пустой = не коммитить) |
| `./deploy.sh --dry-run` | только показать, ничего не менять |
| `./deploy.sh --yes "..."` | не спрашивать подтверждение на удаления |
| `./deploy.sh --no-backup "..."` | без резервного пуша на GitHub |

Двойным щелчком из Finder тоже работает, если переименовать в `deploy.command`.

## Что скрипт делает по шагам

1. **Снимает залипшие замки git.** Это была главная причина «коммит не проходит»:
   песочница Claude не может удалить `.git/index.lock`, и он блокирует все
   последующие коммиты из всех чатов. Замок моложе двух минут скрипт не трогает —
   там может работать живой процесс, и он честно об этом скажет.
2. **Проверяет ветку.** Работа идёт в `hybrid-v8`. Если рабочая копия на другой ветке —
   отказывается и не переключает сам: переключение вслепую уже приводило к потере правок.
3. **Коммитит правки** в `site/` и документацию — по именам файлов, поштучно.
   Никогда `git add -A`: так в коммит попадает работа соседнего чата. Всё, что лежит
   вне `site/` и документации, скрипт покажет отдельно и коммитить не станет.
4. **Заливает `site/` на timeweb** через `rsync` — только изменившееся, минуя GitHub.
   Сравнение по контрольной сумме, а не по времени файла: быстрая сверка молча
   пропускает правку, если размер не изменился и файл правили в ту же секунду, что
   предыдущий деплой. Проверено — так теряется правка.
5. **Пишет в `DEPLOY-LOG.md`**: дата, ветка и хеш, коммиты поставки, список уехавших файлов.
6. **Пушит `hybrid-v8` на GitHub как резерв.** Не прошло — не беда, на сайт не влияет.

## Важно: уезжает диск, а не коммит

`rsync` заливает папку `site/` **как она лежит на диске** — вместе с незакоммиченными
правками и даже с файлами, которых в git вообще нет. Это удобно (что видишь, то и на
сайте), но в общей папке это значит: **чужая недоделка из соседнего чата тоже уедет**.
На проверке так и вышло — в поставку попал `enemy-lab.html`, которого ещё нет в git.

Поэтому перед деплоем скрипт показывает список незакоммиченного, а всё, что лежит
вне `site/` и документации, помечает отдельно. Если в списке чужое и не готово —
не деплой, спроси владельца файла. Посмотреть заранее: `./deploy.sh --dry-run`.

## Что на сервере никогда не удаляется

`rsync --delete` снимает с сервера всё, чего нет в `site/`. Кроме этого:

| Путь | Почему нельзя тронуть |
|---|---|
| `old/` | слепок старого вордпресса, 646 файлов, 244 МБ — живёт только на сервере |
| `.git/` | остаток прежнего git-клона |
| `.well-known/` | подтверждение SSL-сертификата |
| `api/config.php` | ключи модели и пароль почты |
| `api/sessions/` | стенограммы разговоров с посетителями |
| `api/outbox/` | письма, ещё не отправленные |

Список живёт в `deploy.sh`, в блоке `EXCLUDES`. Добавляешь на сервер что-то, чего нет
в репозитории, — вписывай туда же, иначе следующий деплой это снесёт.

## Если что-то пошло не так

**«Another git process seems to be running»** — залипший замок. Скрипт снимает его сам,
но если запускаешь git руками: `rm -f .git/index.lock`.

**«не подключиться к серверу»** — проверь SSH отдельно:
`ssh pdisplay@vh432.timeweb.ru`. Если не пускает — дело в доступе, не в скрипте.

**«rsync не понимает нужные флаги»** — на свежих macOS системный `rsync` подменён на
`openrsync`, который не знает `--itemize-changes`, `--filter` и `--chmod`. Скрипт ловит это
до заливки, а не посреди неё. Лечится:

```bash
brew install rsync
```

и строкой в `deploy.conf`: `RSYNC_BIN="/opt/homebrew/bin/rsync"`.

**«BRANCH: unbound variable» или похожее падение на переменной** — было один раз:
`/bin/bash` на macOS это версия 3.2 от 2007 года, и она не разбирает многобайтные
символы в именах переменных. В строке вида `«$BRANCH»` кавычка-ёлочка прилипала к имени.
Исправлено фигурными скобками — `«${BRANCH}»`. Если правишь скрипт и вставляешь
переменную рядом с кириллицей или типографскими кавычками, всегда пиши `${VAR}`.
В bash 5, где такие вещи проверяются, ошибка не воспроизводится.

**Правка не приехала на сайт** — посмотри последнюю запись в `DEPLOY-LOG.md`: если файла
нет в списке отправленных, он не изменился с точки зрения git. Проверь, что правил файл
в `site/`, а не его дубль в корне.

**Уехало лишнее** — история цела. Вернуть прошлое состояние файла:
`git log --oneline -- site/файл`, затем `git checkout <хеш> -- site/файл` и снова деплой.

## Откуда взялась эта схема

Раньше доставка была цепочкой из трёх звеньев: коммит в `hybrid-v8` → пересборка ветки
`gh-pages` → пуш на GitHub → `git pull` на сервере. Каждое звено могло встать, и вставали
все по очереди: залипшие замки git блокировали коммиты, незапушенные коммиты копились
на двух ветках, пересборка `gh-pages` прямо в рабочей папке разложила сайт в двух копиях,
а `git add -A` затащил в ветку раздачи 1.5 ГБ архива, который поехал на боевой сайт.

Теперь звено одно: `rsync` с Мака на сервер. GitHub остался резервом истории.
